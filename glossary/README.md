# واژه‌نامه

این واژه‌نامه تعریف‌های کوتاه و کاربردی از مفاهیم تکرارشوندهٔ پروژه است. تعریف‌ها برای هماهنگ‌کردن زبان فصل‌ها نوشته شده‌اند و جای مستندات رسمی ابزارها یا کتاب اصلی را نمی‌گیرند.

| اصطلاح | تعریف کاربردی |
| --- | --- |
| **`data-intensive application`** | برنامه‌ای که حجم، سرعت تغییر یا ساختار data مسئلهٔ اصلی آن است. |
| **`reliability`** | system در برابر fault هم رفتار درست خود را حفظ کند. |
| **`scalability`** | با رشد load، روش قابل‌قبولی برای افزایش ظرفیت داشته باشیم. |
| **`maintainability`** | فهمیدن، اجراکردن و تغییر system در طول زمان آسان بماند. |
| **`fault`** | انحراف یک component از spec؛ الزاماً به معنی failure کل system نیست. |
| **`failure`** | وقتی کل system سرویس مورد انتظار را به user نمی‌دهد. |
| **`resilience`** | توان ادامه‌دادن یا recovery بعد از fault. |
| **`latency`** | مدت‌زمان دریافت response. |
| **`throughput`** | مقدار کاری که system در واحد زمان انجام می‌دهد. |
| **`load`** | فشاری که request، data یا connection روی system می‌آورد. |
| **`schema`** | قرارداد fieldها، typeها و معنی data. |
| **`query`** | درخواست خواندن، ترکیب یا تغییر data. |
| **`index`** | ساختار کمکی برای پیدا کردن data سریع‌تر. |
| **`transaction`** | گروهی از operationها که باید تحت قرارداد مشخصی مانند atomicity و isolation اجرا شوند. |
| **`atomicity`** | یا همهٔ operationهای یک unit انجام می‌شوند یا هیچ‌کدام اثر نهایی ندارند. |
| **`isolation`** | میزان جدا دیده‌شدن اثر transactionهای هم‌زمان. |
| **`serializability`** | نتیجهٔ اجرای هم‌زمان مثل یک ترتیب معتبر و ترتیبی باشد. |
| **`replication`** | نگه‌داری چند copy از data یا log برای availability و تحمل fault. |
| **`leader` / `follower`** | leader write را ترتیب می‌دهد و follower تغییرها را دنبال می‌کند. |
| **`replication lag`** | فاصلهٔ زمانی یا ترتیبی میان جدیدترین تغییر و یک replica. |
| **`quorum`** | حداقل تعداد response لازم برای معتبر دانستن operation. |
| **`partition`** | بخشی از dataset با مالکیت یا پردازش مشخص. |
| **`sharding`** | نام رایج تقسیم افقی data بین shardها. |
| **`rebalancing`** | جابه‌جایی مالکیت partitionها بعد از تغییر node یا load. |
| **`normalization`** | کم‌کردن duplication و نگه‌داشتن source اصلی در یک محل معتبر. |
| **`denormalization`** | duplication کنترل‌شده برای سریع‌ترشدن read، همراه با مسئولیت sync و rebuild. |
| **`hotspot`** | key یا partitionای که سهم نامتناسبی از load را می‌گیرد. |
| **`consistency`** | قراردادی دربارهٔ اینکه read چه نسخه‌ای از data را می‌بیند. |
| **`eventual consistency`** | اگر write جدیدی نیاید، replicaها در نهایت همگرا می‌شوند. |
| **`linearizability`** | هر operation انگار در یک لحظهٔ مشخص و در ترتیب واقعی اجرا شده است. |
| **`consensus`** | چند node روی یک value، order یا decision توافق می‌کنند. |
| **`causality`** | رابطه‌ای که نشان می‌دهد یک event می‌تواند علت event دیگر باشد. |
| **`partial failure`** | بخشی از system خراب است و بقیه هنوز کار می‌کنند. |
| **`Byzantine fault`** | component می‌تواند رفتار دلخواه یا دروغ‌گو داشته باشد. |
| **`encoding`** | تبدیل structure data به byte یا text برای storage یا انتقال. |
| **`schema evolution`** | تغییر schema در حالی که data یا consumer قدیمی هنوز وجود دارد. |
| **`message passing`** | ارتباط processها با send و receive کردن message. |
| **`log`** | دنبالهٔ مرتب و ماندگار از eventها یا تغییرها. |
| **`batch processing`** | پردازش یک dataset موجود در قالب job. |
| **`stream processing`** | پردازش پیوستهٔ eventهایی که وارد می‌شوند. |
| **`CDC`** | تبدیل تغییرهای database به event. |
| **`event sourcing`** | نگه‌داشتن eventها به‌عنوان source اصلی و ساخت state با replay. |
| **`materialized view`** | نتیجهٔ ذخیره‌شدهٔ یک محاسبه برای read سریع‌تر. |
| **`end-to-end argument`** | تضمین نهایی باید در دو سر operation هم بررسی شود. |
| **`event time`** | زمانی که event واقعاً در source رخ داده، نه زمان دریافت. |
| **`window`** | بازه‌ای که eventها برای محاسبه یا join در آن گروه‌بندی می‌شوند. |

## روش‌ها و اصطلاحات حساس

### `idempotency`

**چیست؟** یعنی اگر یک درخواست را دوبار یا ده‌بار اجرا کنیم، اثر نهایی آن بیشتر از یک‌بار نشود.

**مثال ساده:** کاربر روی «پرداخت» دوبار کلیک می‌کند. هر دو درخواست یک `idempotency key` یکسان دارند؛ سرویس یک پرداخت را ثبت می‌کند و برای درخواست دوم همان نتیجه را برمی‌گرداند.

**اشتباه رایج:** `idempotency` به معنی بی‌خطابودن عملیات نیست. فقط جلوی چندبرابرشدن اثر یک عملیات تکراری را می‌گیرد.

### `document`

**چیست؟** یک بستهٔ داده که معمولاً با هم خوانده می‌شود و می‌تواند فیلدهای تو‌در‌تو داشته باشد.

**مثال ساده:** مشخصات یک سفارش، آدرس ارسال و اقلام آن می‌توانند در یک `document` کنار هم قرار بگیرند.

**خطر:** اگر یک بخش از `document` در چند جا کپی شود، تغییر آن می‌تواند نسخه‌ها را از هم جدا کند.

### `relational`

**چیست؟** مدلی که داده را در tableها و رابطه‌های مشخص بین آن‌ها ذخیره می‌کند.

**مثال ساده:** جدول مشتری جداست، جدول سفارش جداست و `customer_id` رابطهٔ آن‌ها را نشان می‌دهد.

**خطر:** اگر queryها به joinهای بسیار بزرگ نیاز داشته باشند، هزینهٔ خواندن و scale کردن بیشتر می‌شود.

### `normalization` و `denormalization`

**`normalization` چیست؟** دادهٔ اصلی را طوری در چند table یا entity می‌چینیم که یک حقیقت بی‌دلیل در چند جا تکرار نشود. در نتیجه، تغییر یک مقدار معمولاً فقط در یک محل انجام می‌شود و بعد با `join` رابطه‌ها را می‌سازیم.

**`denormalization` چیست؟** بخشی از data را آگاهانه تکرار یا کنار هم ذخیره می‌کنیم تا readهای مهم سریع‌تر و ساده‌تر شوند. در عوض، باید update چند نسخه، ناسازگاری و روش بازسازی را مدیریت کنیم.

**تفاوت مهم:** `normalization` و `denormalization` دربارهٔ شکل و تکرار data هستند؛ `rebalancing` دربارهٔ جابه‌جایی مالکیت `partition`ها میان nodeهاست. این سه اصطلاح جای یکدیگر نیستند.

### `outbox`

**چیست؟** یک table یا محل ثبت event که در همان transaction تغییر business state نوشته می‌شود.

**چرا لازم است؟** اگر database موفق شود اما publish به broker شکست بخورد، بدون outbox سیستم‌ها از هم جدا می‌شوند.

**چطور کار می‌کند؟** transaction هم state اصلی و هم رکورد outbox را commit می‌کند؛ publisher بعداً outbox را می‌خواند و event را می‌فرستد.

**اشتباه رایج:** outbox duplicate را حذف نمی‌کند. publisher و consumer همچنان باید با retry و اجرای دوباره کنار بیایند.

### `saga`

**چیست؟** یک workflow چندمرحله‌ای که هر مرحله transaction خودش را دارد و برای شکست، action جبرانی تعریف می‌کند.

**مثال ساده:** رزرو اتاق، گرفتن پرداخت و ارسال confirmation سه مرحله‌اند. اگر پرداخت شکست بخورد، reservation آزاد می‌شود.

**خطر:** جبران همیشه معادل rollback نیست؛ ممکن است refund، اعلان یا بررسی انسانی لازم باشد.

### `retry`, `timeout`, `backoff` و `jitter`

- `timeout`: مهلت پاسخ؛ تمام‌شدن آن فقط می‌گوید نتیجه هنوز معلوم نیست.
- `retry`: تلاش دوباره فقط برای خطای موقت و با سقف مشخص.
- `backoff`: زیادکردن فاصلهٔ retryها برای کم‌کردن فشار.
- `jitter`: اضافه‌کردن تغییر کوچک تصادفی تا همهٔ clientها هم‌زمان retry نکنند.

ترکیب این چهار واژه باید کنار `idempotency` تعریف شود؛ retry بدون آن می‌تواند یک side effect را چندبار اجرا کند.

### `CDC`

`CDC` مخفف **Change Data Capture** است. یعنی تغییرهای database، مانند insert یا update، به event تبدیل شوند تا search index، cache یا analytics از آن‌ها استفاده کنند. `CDC` منبع حقیقت جدیدی نیست؛ فقط راهی برای بیرون‌کشیدن تغییر از منبع اصلی است.
